# How to build and benchmark TRACE Computer Use on Windows

This guide rebuilds the TRACE skill and Windows executor, then compares it with bundled Codex Computer Use on one owned WinForms control. The implementation is in [PR 172](https://github.com/mogesjohnson/trace-workbench/pull/172) and [PR 173](https://github.com/mogesjohnson/trace-workbench/pull/173).

## Rebuild the skill from an empty directory

1. Create a Node project. Use the Node versions in [package.json](package.json) and Windows x64 with the .NET 10 SDK and Desktop runtime. Use [the lockfile](package-lock.json) for exact dependency versions. The Windows executor uses MCP 2.3.1 over stdio, Zod schemas and winapp CLI 0.7.1. [Winapp version and hashes](src/computer/winapp-pin.json)
2. Create `trace-computer-use/SKILL.md`. Add YAML frontmatter with `name: trace-computer-use` and a `description` covering the tasks it handles. In the body, route to a connected application API when it can perform the task, then to structured browser tools for web targets, then to native input for Windows windows. Write the native sequence doctor → exact discovery → open → observe → one action → verify → close. Explain how to choose image mode, depth, scope and response size. [Canonical skill](skills/trace-computer-use/SKILL.md)
3. Add the three supporting references. Put capability selection and missing-tool handling in [readiness and routing](skills/trace-computer-use/references/readiness-routing.md). Put freshness, owned dialogs, uncertain delivery and cleanup in [operation and recovery](skills/trace-computer-use/references/operation-and-recovery.md). Put test gates and effect verification in [acceptance](skills/trace-computer-use/references/acceptance.md). Record the four authored files in [the manifest](skills/trace-computer-use/manifest.json) with their raw-byte SHA-256 hashes.
4. Implement the seven public tool schemas in [server.cjs](src/computer/server.cjs). Open accepts a returned window ID. Observe accepts a session ID and requested evidence. Act accepts the latest observation ID, one strict action and the requested refresh form. Send structured state and a separate MCP image block for each screenshot. Store each image's content index and physical dimensions in the state so clients can bind it to the observation.
5. Build the [controller](src/computer/controller.cjs) around one leased target. Pin HWND, PID, process creation time and Windows session. Serialize desktop work. Store the observation ID, geometry, tree, scope and expiry on the server. Consume the ID before dispatch. Revalidate window and element identity before input and verify effects against application state. Use fresh evidence and the same binding when following owned dialogs.
6. Implement the [Windows adapter](src/computer/winapp-backend.cjs) with public Win32, DWM and UI Automation surfaces. Use window-scoped capture, normalize physical bounds, and bracket the capture with identity and geometry checks. Reject occluded points. Generate fresh evidence after an action. Separate input delivery from the result of the subsequent refresh so a lost refresh cannot lead to an automatic replay.
7. Build the [native session owner](native/TraceSupervisor/Session.cs) with private inherited stdio. Acquire the exclusive desktop lease, start the visible [indicator](native/TraceActivityIndicator/Program.cs) and install physical Escape handling. Run mutating providers in kill-on-close jobs. Record declared inputs and the child identity before resuming the process. On interruption, drain or terminate owned work and verify input release. Retain durable recovery when cleanup is uncertain.
8. From the repository root, run `npm ci`, `npm run computer:setup -- --plan`, `npm run computer:setup -- --apply` and `npm run computer:doctor`. Setup builds and hashes the native helpers under `.runtime/`. Run `npm run computer:config -- --plan --client codex --client claude_code`, then apply the same scope with `--apply`. Reload MCP in both clients. Each client discovers the authored skill and launches `bin/trace.cjs computer mcp` over stdio. [Install and connect](docs/COMPUTER_USE.md#install-and-connect)

## Compare the two skills one step at a time

Scope this comparison to a Windows window that is already open. TRACE also routes work to connected APIs and browser tools. The Codex reference is the bundled Windows Computer Use skill and its supported `@oai/sky` window API. TRACE's authoring entry point is [its skill](skills/trace-computer-use/SKILL.md), and [the MCP reference](docs/COMPUTER_USE.md) defines its runtime contract.

| Step | Codex Windows Computer Use | TRACE Windows Computer Use |
| --- | --- | --- |
| 1. Initialize | Import `{ sky }` from `@oai/sky` in a persistent `node_repl` session. The packaged JS proxy asks the trusted runtime for its supported methods. | Discover the MCP tools and call `trace_computer_doctor` before starting a native session. Doctor reports provider readiness and supported actions. |
| 2. Select exactly one window | Call `sky.list_windows()`, or find the app and its windows with `sky.list_apps()`. Select the exact returned window. Use `get_window({ id, app })` to rehydrate the returned identity when needed. | Narrow `trace_computer_list_windows` by process name or title, then choose the exact returned ID. When launching is needed, rediscover the returned target. |
| 3. Prepare the target | The guidance example calls `activate_window` once during setup. The API also documents that input methods activate their own target. | Open the exact window with `trace_computer_open_session`. The native supervisor owns the desktop lease and indicator. The controller and native backend revalidate the target at input time. |
| 4. Observe | Call `get_window_state({ window, include_screenshot: true, include_text: true })` once for image and tree. Save the returned window, tree index, and screenshot ID from that state. The wrapper makes one native state request and emits its images through the host. | Call `trace_computer_observe` in full mode with `screenshot: "full"` and depth 2. Retain the session ID, single-use observation ID, selected element ID, and physical bounds. The installed 2.3.0 backend reads geometry, UIA, capture, related windows, identity and focus through multiple supervised calls. |
| 5. Click once | Call `sky.click` with the returned window and current element index, adding the screenshot ID on the benchmark path. The JS wrapper issues one element-click request. | Call `trace_computer_act` with the session ID, observation ID, and exact element ID. In 2.3.0 this repeats target and geometry validation, prepares activation, checks pointer occlusion, then dispatches the click. |
| 6. Refresh immediately | In the same cell as the click, call `get_window_state` again with both flags. Use the fresh evidence for the next decision. | `act` performs the refresh internally. Pass `returnObservation: "full"` to get the complete result with its inherited screenshot setting. |
| 7. Verify the effect | Compare the fixture's independently written counter before and after. | Apply the same counter check. An action receipt and fresh observation are separate from proof of the intended effect. |
| 8. Recover and release | Recover a lost window binding from returned identity or fresh discovery. Reobserve after uncertain delivery. The packaged client has host end-of-turn handling. | Classify `not_dispatched` and `unknown` separately, then verify uncertain delivery before any new action. Close the session and confirm lease release and native cleanup. |

The Codex screenshot-only default skips accessibility text. The benchmark explicitly requests both on both screenshot-backed reads. TRACE's image-free full observation still grants one action. Its separate accessibility-only and screenshot-only modes are evidence-only. Use the complete screenshot-backed paths when evaluating parity. A screenshot-free element click in the original Codex warm-up failed for missing coordinate geometry, with no observed effect.

## Reproduce the REA inspection

1. Record the installed Codex application version, bundled skill version and Sky package version. The measured host had app `26.1106.6628.0`, skill `26.1106.51428`, and the packaged `@oai/sky` manifest declares `0.7.18`. On Windows, get the app installation root from `Get-AppxPackage -Name OpenAI.Codex`. The inspected Sky package is under `app/resources/cua_node/bin/node_modules/@oai/sky`.
2. Call REA `analyze_javascript_application` with the absolute package directory as `input_path`, `detail: "summary"`, and exact `source_paths`. Select `package.json` and the files below under `dist/project/cua/sky_js/src/`:
   - `index.js`, `sky.js`, `sky_service_rpc.js`, `service.js`, `create_client.js`, and `load_options.js`
   - `targets/windows/create_client.js`
   - `targets/windows/internal/computer_use_client_base.js`, `computer_use_client.js`, and `helper_transport.js` in the same internal directory
3. Use the returned parent Evidence ID with `inspect_analysis_view` and `kind: "javascript-facts"` on the selected client and transport modules. Record module paths and digests. Trace the shipped entry point through setup and per-method calls to the cached client. Read the Windows wrapper's observation, element-click and transport branches. Export the retained REA bundle to a local scratch directory.
4. Confirm the public workflow by timing the supported `sky` API in `node_repl`. The static inspection executes no package code. The benchmark calls the supported API and needs no direct helper invocation.

The scoped REA analysis used inventory SHA-256 `970c7cac62126410c92c1cda4282a9e1e5f4a6b13f060f6a0d0800e5c39f0ff9`. Parent Evidence `ev_bc8e5c58f3e4931deebe9f82f81bce702b53a1e151b997338d55ac0653450324` analyzed ten JavaScript modules and the manifest, leaving 239 inventoried files outside scope. The transport module facts view is `ev_57930a47ec3dd113eec63736c96c9f6f0e1fe8fe2b92b50dfd84ac10c5454e0b` from the initial scoped analysis of the same artifact.

The shipped proxy uses trusted host RPC, the service retains a default client across calls, and the Windows client can either reuse a shared lazily started child transport or keep a serialized host-managed connection. Both branches amortize setup. This inspection establishes the JS request boundaries. Which native transport served the timing run and how much time native UIA, capture, activation, or input spent individually remain unmeasured. The TRACE full observation already describes Windows Graphics Capture with checked frame geometry. Its separate screenshot-only mode uses PrintWindow.

## Reproduce the Codex reference run

1. Build `tests/fixtures/computer-app/TraceComputerFixture.csproj` in Release for the Windows .NET target declared there. [The live smoke script](scripts/smoke-computer-live.cjs) has an existing `buildFixture` helper. Start the owned fixture with `--run-id <unique-id> --receipt <absolute-fixture.json> --commands <absolute-commands.json>`. Use an existing scratch directory. Keep the child PID and verify the exact title `TRACE Computer Fixture — <unique-id>`.
2. Use a clear unlocked desktop, the same fixture instance and unchanged DPI/window position. Import the bundled Sky module and select one exact returned window in `list_windows`. Rehydrate its returned `id` and `app`, then activate it outside the timed region. Check that the intended button is visible. Allow an excluded warm-up with the full screenshot-backed sequence.
3. Time text-only observation in its own cell with `include_text: true, include_screenshot: false`. For the timed cycle, take a fresh screenshot-and-text observation, inspect its tree and find the current index of the fixture's Increment button. Use its returned window and screenshot ID. Time `click` followed immediately by a new screenshot-and-text state in the same cell.
4. Measure both actual tool-call wall time and, when possible, each `sky` call with `performance.now()` inside the cell. Time the post-click observation as its own stage. Compute each cycle as that sample's pre-click observation plus its click-and-refresh. Compute medians across samples only after forming sample totals.
5. Read the independent fixture receipt outside timing and require one increment per timed click. Keep failures and warm-ups in the record with their classification. Stop after uncertain delivery until the fixture receipt resolves the effect. End the computer-use work, release each TRACE lease between providers, and close only the owned fixture and test clients.
6. Retain raw samples and disclose trial order, versions, observation settings, time boundaries, and cleanup. The original order was Codex ×3, TRACE screenshot ×5, Codex ×2, then TRACE lean ×5. For a new comparison, alternate provider blocks and use the same exact checks. Keep setup, assistant deliberation, independent effect checks, and cleanup out of timed samples.

For reference, the original Codex host medians were 269 ms text-only, 148 ms screenshot and tree, 266 ms click plus screenshot-backed refresh, and 431 ms for the complete screenshot-backed cycle. The cycle ranged from 347 to 803 ms. Inside the JavaScript cells, the medians were 105.944 ms for the screenshot-and-tree observation, 99.306 ms for the click, 131.923 ms for post-click observation, and 351.655 ms for the complete cycle. These are fixture-specific timings and the stage medians describe separate distributions.

## Profile the original TRACE path

1. Build the fixture with `node -e "require('./scripts/smoke-computer-live.cjs').buildFixture().then(console.log)"`. Start it in a private scratch directory using the arguments above. Capture the PID and exact title.
2. Wrap `NativeSupervisor.run` to measure each call with `performance.now()`. Record provider, verb, stage, mutation flag and duration. Wrap the controller's `observe` and `act` methods to mark call boundaries and the backend methods of the same names to distinguish dispatch from refresh. Keep stdout for MCP. Log numeric data without command arguments, UI contents or images. Require the exact fixture PID and title and permit only the selected Increment counter action.
3. Start the instrumented server over stdio using `runComputerServer({ controller })`. The client calls doctor, lists by fixture title and opens the exact returned ID. For text-only, request `mode: "full", accessibilityDepth: 2, screenshot: "none", metrics: true`. For the screenshot sample change `screenshot` to `"full"`. Select the unique enabled `Increment counter` element. Act with `{ type: "click", elementId }` and `returnObservation: "full"`. Verify each screenshot's content index references an image block in the same result.
4. Exclude one warm-up and take at least five valid samples. Check the independent fixture receipt for exactly one increment after each click. In `finally`, close the session and require `cleanup: "confirmed"`, close stdio and confirm fixture exit. Run `node bin/trace.cjs computer recover --check` and require `recoveryRequired: false`.
5. Group durations by stage within each sample, then take medians. The baseline made 9 supervised requests for text-only observation, 10 for image and UIA, and 17 for click and refresh. Backend dispatch took 1,141 ms and backend refresh took 1,528 ms at the median. Two controller identity reads contributed a further 268 ms. These native command timings cover launch, execution and supervised completion.

The full baseline cycle used 27 child jobs, including thirteen for identity or geometry. The screenshot observation's three bounds reads totaled 434 ms at the median. Its two UIA inspections totaled 466 ms, and capture took 203 ms. After click, UIA inspections totaled 471 ms and capture took 217 ms. The pinned winapp click waits 100 ms after requesting the foreground and 50 ms after moving the cursor. [Microsoft winapp 0.7.1 click implementation](https://github.com/microsoft/winappCli/blob/e3cd0b94f3e7b776ac51ba0564f4908094e979b5/src/winapp-CLI/WinApp.Cli/Commands/UiClickCommand.cs)

## Apply the measured changes

1. Extract the guarded HWND read to `native/TraceSupervisor/WindowRead.cs` as in PR 172. Validate the verb, HWND and PID. Read process lifetime, session and owner, and return either the exact title or Win32 outer and DWM frame rectangles. Use per-monitor-v2 awareness on the calling thread for geometry and restore the previous context in `finally`. Recheck HWND and owning process before returning.
2. Compile the same code into the standalone bridge and supervisor. The bridge supplies its activation callback only for the activation command. Include the shared source in both source/output manifests. Run `npm run computer:setup -- --apply` to rebuild and verify the artifacts.
3. In the session owner, use the in-process path only for `identity` and `bounds`. Keep serialization, the recovery gate, reply format and JS receipt validation. Check stop before reading and cancellation before returning. Keep UIA, capture, activation and mutations in their owned child jobs. The cycle still makes 27 supervised requests, with only 14 launching children.
4. Change the private post-observation UIA recheck to depth zero as in PR 173. Compare the fresh root rectangle with the original and keep the independent Win32 geometry comparisons. Preserve the caller's requested depth for visible evidence and action validation. Verify a changed root rectangle still rejects the observation.
5. Run `npm run check`, focused backend, observation and supervisor tests, native bridge and supervisor self-tests, and `npm run test:computer:mcp`. Run the exact owned fixture separately. A broader release also needs coverage for moved and minimized targets, owned modals, overlapping windows, deep elements, display scaling, physical stop and fresh host sessions.

The TRACE cycle improved 43.0% against the direct baseline. The combined candidate took about 6.6× the latest Codex cycle time. Each timed action incremented exactly once and every owned fixture exited. The direct TRACE runs used `f2153fc` with installed 2.3.0 helpers, `94ee4ca` for the first change and `cf38dd7` for both. The original and direct TRACE measurements used different time boundaries and run conditions, so those values do not isolate host overhead.

The public WinApp UI Automation 0.7.1 SDK can group UIA inspection, screenshot capture, PNG encoding, fresh root verification and focus in one warm process. A standalone fixture probe measured 250 ms with a depth-one recheck and 215 ms with depth zero. At depth zero, medians were 119 ms for the tree, 31 ms for capture, 6 ms for encoding, 56 ms for root verification and about 1 ms for focus. This probe exercised the SDK read path only. [Pinned public SDK guide](https://github.com/microsoft/winappCli/blob/e3cd0b94f3e7b776ac51ba0564f4908094e979b5/src/winapp-CLI/WinApp.UIAutomation/PACKAGE.md)

To reproduce the probe, create a .NET 10 console project targeting `net10.0-windows10.0.19041.0` and enable WPF for PNG encoding. Pin `Microsoft.Windows.SDK.BuildTools.WinApp.UIAutomation` to 0.7.1 and `Microsoft.Extensions.DependencyInjection` to 10.0.0. Register `AddWinAppUiAutomation()` with logging, resolve `IUiAutomation`, and build an explicit `UiTarget` from the owned HWND. In one process, call `InspectAsync` at depth 2, `ScreenshotAsync` with the observed root selector and both screen-capture and focus flags false, encode BGRA with `PngBitmapEncoder`, read the root again at depth 0 and compare its four bounds coordinates, then query `GetFocusedElementAsync`. Exclude one warm-up. Verify the fixture count remains zero and close the fixture.

## Same-window cross-check

Keep one fixture instance open across provider blocks. Confirm the TRACE lease is closed before activating the fixture with Sky, and end the Sky session before opening the candidate TRACE lease. Use the same increment control throughout and check the independent counter after every timed click. The cross-check used this order and excluded one warm-up per block.

| Implementation | Trials | Text only | Screenshot and UIA | Click and refresh | Screenshot-backed cycle |
| --- | ---: | ---: | ---: | ---: | ---: |
| TRACE 2.3.0 direct MCP | 3 | 1284 | 1481 | 2740 | 4212 |
| Codex host | 5 | 90 | 120 | 305 | 426 |
| TRACE with both changes, direct MCP | 5 | 629 | 842 | 1684 | 2538 |

The combined candidate reduced the same-window TRACE cycle by 39.7% and took about 6.0× the Codex host median. All 13 timed clicks incremented exactly once. Both TRACE leases closed with confirmed cleanup, recovery was clear, the Codex kernel was reset, and the fixture exited. The two provider timings still use different client boundaries.

A separate live guard check moved and minimized an owned fixture using its command file after observation. Both stale clicks returned `not_dispatched` with `window_moved` and left the counter unchanged. A fresh screenshot-backed observation enabled exactly one click in each case, including restore from minimized. Session close and recovery checks passed.

The next parity experiment needs a managed lifetime for a read-only worker, bounded UIA property caching and one fresh WGC frame per observation. Keep the evidence tied to the pinned HWND and compare frame and root geometry before granting input authority. Design the click job around final foreground, geometry, element and hit-test validation followed by one declared input sequence. Measure each change independently. Before claiming parity, alternate multiple blocks and retain equivalent timing and correctness evidence.
